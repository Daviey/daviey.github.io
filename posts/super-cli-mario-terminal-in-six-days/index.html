TL;DR: one deterministic engine drives a terminal, a browser, an APK, an iOS .ipa, a UEFI boot image and a from-scratch SSH arcade, with a replay-verified leaderboard that nobody can lie to. Every number below is measured in-tree; every bug in the final section was hit by a real player.

On 25 August 2026 I tagged v0.1.0 of SUPER CLI MARIO, a complete Super Mario Bros. style platformer that renders in a plain terminal. On 30 August I tagged v0.7.1. In the six days between them: 339 commits, 34,430 lines of Go (17,270 of those lines are tests), zero external dependencies, and a game you can play by typing ssh mario.baby, or just by opening https://mario.baby in a browser, with no client install, no account and no download.

This post is the technical side of that: the decisions that shaped the codebase, the numbers that came out of it, and the bugs that only a machine could catch.

What it is

SUPER CLI MARIO is an SMB-style platformer: seven levels across two worlds and four themes (overworld, underground, sky, castle), with mushrooms, fire flowers, star power, hidden blocks, piranha plants, paratroopas, fire bars, lava, checkpoints and a flagpole sequence. It draws truecolor pixel art using half-block terminal glyphs, two square pixels per character cell, with a custom 3x5 arcade font for the HUD. It has an online leaderboard, a daily generated challenge, a browser build, an Android APK, an iOS .ipa, macOS and Linux packages, a bootable UEFI image, and an SSH game server that turns any machine into an arcade.

All of it is one Go module, github.com/Daviey/mario, using only the standard library. The engine, the renderer, the SSH server, the Supabase client, the WASM build, even the .deb and .rpm packagers. Go 1.22 or newer, CGO_ENABLED=0 everywhere.

That constraint was inherited, not chosen for its own sake: the game began life as a library to hide inside another Go program. The zero-dependency rule and the clean library facade are that origin fossilised into architecture (what that bought, later).

Determinism came first

The design decision everything else hangs on is that the engine is fully deterministic. Game.Update(Input) advances exactly one tick at a fixed 60 Hz. There is no math/rand and no time.Now() anywhere in the engine or render logic. Blinking question blocks, the star power palette flicker, the fire bar angle: all of it is a pure function of the tick counter. Identical input sequences reproduce identical games, pixel for pixel.

Why pay for that property? Two consumers turned out to need it.

The first is the test suite. The determinism tests re-run the scripted demo playthrough and byte-compare the full rendered ANSI output against a reference. Any hidden clock, any floating point wobble, any map iteration order leaks straight into a diff.

The second is the leaderboard. Every run is recorded as an input log, the recording is submitted with the score, and a verifier replays the inputs through the same engine. If the replay reproduces the claimed score, level and engine version, the row is kept. If not, it is deleted.

You can cheat the physics with a debugger, but you have to cheat 130,000 recorded ticks.

Determinism is also a cost. Physics is written in a way that never depends on frame time, entity iteration order is fixed, and the level builder rounds carefully (the piranha plant markers live at float-adjacent coordinates and a plain int() truncation shifts a marker one column off its pipe). The 114 functions in engine/ are boring on purpose.

Pixels in a terminal

The terminal is a hostile framebuffer. A character cell is roughly 1:2 tall, so the renderer maps two square pixels into each cell with the half-block glyph ▀: the upper pixel in the top half, the lower in the bottom. A solid vertical pair (upper colour equals lower colour) is rendered as a space with a background colour, which is cheaper to diff and reads cleaner.

Colour depth is three-tier. Terminals that identify as truecolor get 24-bit SGR. Terminals that advertise 256 colours get the fixed xterm cube, with palette indices chosen as OKLab-nearest matches so saturated reds stay saturated instead of washing out. Everyone else gets an honest base-16 fallback, and -basic forces it.

The cube mapping does real colour-space maths. The xterm cube (216 colours, six levels per channel) and the 24-step gray ramp are spec-fixed. Every terminal renders them identically no matter how the user's profile configures the 16 base colours, which is why the base colours are excluded as candidates. Tango's "red" is #EF2929, Solarized's is #DC322F; trusting either is how you get washed-out reds. Each palette colour is mapped to its nearest cube entry by distance in OKLab, computed once at palette build. The colour space is the whole trick: plain RGB distance maps the player red #FF3B30 onto cube entry 203 (#FF5F5F, pink), while OKLab's lightness/chroma balance holds it on entry 196, #FF0000.

The bigger win is the wire format. Early on, SGR style sequences were about 80% of every frame. A full-screen redraw at 60 fps is a lot of bytes to push over SSH. The fix was a minimal-diff SGR encoder. Style state persists across cells, runs and rows, so a style is emitted only when it actually changes. A space never carries a foreground colour. Attribute clears that would need partial resets fall back to a full 0;... form. The diff also bridges small clean gaps (12 cells or fewer) by rewriting identical cells when the exact serialised cost, styles included, beats sending a cursor address.

The style comparison is wire-truth, not palette identity. In 16-colour mode, two palette entries that share an ANSI index are the same terminal colour and must not re-emit SGR every frame, while the terminal's default colour is its own wire state and never compares equal to an indexed one, even when the numbers match.

Measured at 60 fps by TestStreamBandwidth, which drives a scripted run through a 198-column, 29-row viewport:

The differential rework cut per-tick bandwidth by roughly 56% over the naive full-frame encoder. Two tests pin the contract: a round-trip test that reconstructs the screen from the emitted byte stream using a simulated terminal model, and a bandwidth test with hard caps. If the stream ever silently regresses to verbose SGR, the caps trip.

Bandwidth is half the performance story; allocation was the other half. The engine itself measures 8 ns per tick with zero allocations, so the hot path was the renderer: per-tick frame buffers. Screens, the world raster and the RGB buffer are now recycled through the stream. Steady-state rendering allocates nothing, which one test pins by failing on any per-tick allocation. The rework cut allocation 778-fold and made the render loop 36% faster (fbce1c1). Delivery: the wasm is 12,070,950 bytes raw and 3,190,927 gzipped (74% of the bytes never leave nginx), and -s -w strips 351 bytes of it: the size is nearly all Go runtime and engine code, not symbols.

The viewport also follows terminal resizes live. Resize can land from any goroutine, the next Step picks it up, and the diff does a full repaint on a size change. There are race tests for concurrent resize and step, plus viewport sweeps: every screen must survive terminal widths from 16 columns up to 60 and heights down to 4 tiles tall, because people actually play in tiny panes.

How the game moves is deterministic too, and that starts with the animation being distance-based, not time-based. The player's WalkDist accumulator adds ground covered each tick, including the friction slide after you release the key (the legs slow down with the body), and the walk-cycle frame is int(WalkDist / 0.55) % len(frames): about a third of a second per cycle walking, under two-tenths running. Enemies waddle on their own accumulator at 0.16 tiles per frame. Jump stretch and landing squash are 6-tick pose timers, a hard landing is any fall over 0.12 tiles per tick, skids kick dust every fourth tick. There's no wall-clock anywhere in the animation, so a replayed run animates identically, byte for byte.

The jump feel is three classic algorithms in tick arithmetic: five ticks of coyote time after walking off a ledge, five ticks of jump buffering before landing, and a jump-cut that clamps velocity to −0.15 when the key is released early (full jump velocity is −0.43 and clears about 4.4 tiles; the reachability bounds elsewhere in this post are derived from those numbers).

Keyboard input in a hostile world

Terminals disagree about keys. Modern ones speak the kitty keyboard protocol, where every press, repeat and release is an explicit CSI ... u sequence (spec). Older ones send a character once and then the OS's autorepeat kicks in, with per-terminal and per-OS cadence that nobody documents.

The input mapper handles both, and latches its regime. A CSI u final byte is unambiguous kitty, so once one is seen the stream is treated as kitty forever after, and typeless presses (ghostty and kitty omit the :1 event type; it's the default) are normalised to presses. Legacy-only streams keep the inference model, where hold windows are calibrated against observed OS repeat cadence.

The nastiest case is single-key-repeat terminals: Wayland compositors, and anything behind tmux (which strips the kitty negotiation), autorepeat only the newest pressed key. Hold right and press jump, and right's repeat stream dies forever. The mapper keeps a demotion model that resurrects proven holds through the silence, with a cap so a stale hold cannot run you off a ledge.

Hold right, press jump: on half the desktops in the wild, right's key repeat never comes back.

The model is bounded on both ends. A demoted hold can be resurrected by a byte for another key within 80 ticks (about 1.3 s) of its expiry, and the jump key's extension is capped at 24 ticks. The full rise takes about 20.5, so the cap leaves slack for an honest held jump without letting a stale hold float you through the ≈41-tick landing.

The kitty keyboard stack turned out to be screen-scoped, which cost a live report to learn. Push the flags after entering the alt screen (?1049h), pop before leaving it (?1049l), both on the alt screen: the first version pushed on the main screen, the epilogue's pop then hit the alt screen's empty stack and did nothing, and the player's shell was left emitting 07;129u… CSI-u garbage after exit. The tempting fix is also wrong: popping after ?1049l targets the main screen's stack and can eat a level a shell integration pushed there (2133c2c).

Keyboard ownership has a single router. While a leaderboard screen is reading keystrokes (typing a name for the board), bytes go to the UI alone, so the mapper never sees the releases for keys still held at that moment. Handing the keyboard over calls ReleaseAll, or a sticky kitty hold would run the next game for you.

The byte-level cousin of that bug dismissed prompts instantly. At game over you are still holding movement keys, and their release sequences arrive as multi-byte escapes; read one byte at a time, a lone 0x1b lands as Enter and the submit prompt vanishes before you ever see it. UI capture now goes through a proper plain-decoder instead of raw single bytes (6db81b7).

And the native runner learned to have one owner of stdin the hard way. A leaderboard prompt reading os.Stdin directly raced the game's own reader for file descriptor 0, and each keystroke went to a random one of them. Half the time the prompt silently ate nothing and looked frozen; a frozen full-screen prompt is exactly how sessions end up killed with terminal modes still pushed (c7506a5).

Your machine is the arcade

mario -serve :1985 turns any machine into a multiplayer arcade (1985 is the year Super Mario Bros. shipped). Players connect with ssh yourhost -p 1985. Any username works. There's no shell, no account, no forwarding. The only service the server provides is the game.

The SSH implementation is written from scratch on the standard library: the transport with curve25519 key exchange and ed25519 host key, aes128-ctr with hmac-sha2-256 in MAC-then-encrypt order (the unencrypted length field must be readable before the MAC can be verified), none authentication, and one session channel per connection. No golang.org/x/crypto, because the zero-dependency rule extends to the network stack. The protocol notes that cost an afternoon each:

  • Modern OpenSSH does not reset packet sequence numbers at NEWKEYS unless strict KEX is negotiated, and this server does not offer strict KEX, so the per-direction counter runs for the life of the connection.
  • CHANNEL_SUCCESS and CHANNEL_FAILURE replies carry the four-byte recipient channel, not the sender's.
  • Teardown order is exit-status, then EOF, then CHANNEL_CLOSE, then a 300 ms grace, then TCP close, because closing with writes in flight gets you a RST.
  • The client's CHANNEL_EOF means stdin is done, not that the session is over, so the server keeps rendering attract mode until the channel actually closes.

Input feel over the wire holds most of the remaining subtlety. Three invariants, each of which was a live bug:

  1. The connection reader goroutine never writes to the socket once frames may be flowing. Keystroke bytes are fed to the game first, and everything the protocol owes back (window adjustments, keepalive replies) rides a separate control pump. A synchronous write behind a frame chunk wedged on a full kernel send buffer stalled input delivery for up to 30 seconds. Accepted connections also set TCP_NODELAY so control packets do not queue on Nagle behind 256 KB frame chunks.
  2. SSH receive-window adjustments coalesce into a lossless owed counter that replenishes at half the 2 MB window, OpenSSH's own policy. Human typing generates zero adjust packets, and any leftover below the threshold simply carries over toward the next adjustment.
  3. The simulation runs at 60 Hz on the tick goroutine, but diffing and writing happen on a writer goroutine with a latest-frame mailbox. A slow link drops rendered frames, never simulation ticks, so keystrokes keep flowing and releases stay on time. Loopback, keypress to output measures about 18 ms, which is one tick.

Mosh support (-mosh auto) proxies the roaming handshake with a strict argv whitelist: the server rebuilds the mosh-server new command with its own binary and port range, and never execs the client's own command line. mosh 1.4 unconditionally overwrites the child's TERM to xterm-256color, so the game's environment strips inherited TERM and COLORTERM and re-sets COLORTERM=truecolor when the SSH phase saw a truecolor terminal. Without that fix, mosh users got the 16-colour palette, which is how "less colours" bugs get reported.

The server also identifies each player's terminal and picks the right colour depth with no config. When a shell session starts, it asks the client terminal to identify itself with device-attribute queries (DA2 CSI > c plus DA3 CSI = c, the trick vim uses for termresponse) and sniffs the reply out of the inbound stream. That is the only reliable way to tell GNOME's VTE from Apple Terminal, which both speak xterm-256color but only one renders 24-bit colour. Precedence is a forwarded COLORTERM environment request, then the TERM family, then the probe. Silent terminals wait at most 250 ms once per connect, pre-title.

Capacity is bounded by -maxsessions (default 16; measured, a single core holds full-quality play to about 16 to 20 concurrent sessions and saturates around 32). Over-capacity players join a FIFO queue showing their position and an ETA computed from Little's law against a session-length EWMA, and are admitted strictly in order via slot transfer under one mutex.

A leaderboard nobody can cheat*

*Not quite nobody. The verifier proves the engine produced the score from a real input sequence; it can't prove a human was holding the keys. A tool-assisted run still verifies, because it genuinely earned the score. What nobody can do is claim a number the game didn't produce.

The very first iteration of the leaderboard was drawn with raw pixel blocks, which we quickly abandoned for readability before it ever saw a public release:

The board is a plain Supabase PostgREST table. There is no game server to run or trust, which is most of the design. Every submission carries the run's replay recording, a device id, an engine version and a 20-bit SHA-256 proof-of-work over device_id:score:nonce, solved client-side in board/pow.go and checked by a verify_pow() trigger. Proof-of-work is the throttle against drive-by inserts from scripts. Twenty bits is about 0.1 seconds for an honest player (well under a second in wasm) and a real CPU cost per row for a scripted flooder, so rotating device ids no longer buys anything.

On top of that: row-level security with a BEFORE INSERT trigger capping anon submissions at 10 per minute per source address (from Cloudflare's cf-connecting-ip) and 2 per minute per device, a board_rows RPC that hides device_id from anonymous readers (mine-ness arrives precomputed), and a nightly pg_cron job that keeps the top 500 rows and drops anything older than 60 days.

The board is also an injection surface, which is easy to forget. The payload is text. The first schema checked name length and nothing else. A probe stored an eight-character name containing an ESC byte (HTTP 201) and an HTML payload (also 201), and the fetch path formatted names straight into the frame. Any anonymous player could have run escape sequences in every other player's terminal. The fix is a charset allow-list (A-Z 0-9 . -, one source of truth shared by name entry, the Go client and a DB CHECK), plus sanitize-on-read so legacy rows can't attack anyone either (36e7c74).

The verifier is a GitHub Action that runs every 15 minutes. mario -verify-pending fetches unverified rows, replays each recording through the deterministic engine, and checks that score, level and engine version all match the row's claim. A match sets verified (the green checkmark on every board surface). A mismatch deletes the row.

A score is a claim. The recording is the proof, and the proof has to replay.

Every deletion carries a reason. A version drop is a row recorded before an engine version bump, expected once per gameplay-changing release, and harmless. A determinism drop means the replay genuinely disagreed with the row's claim: one is a corrupted recording, two means a systematic bug is deleting real scores. Two or more determinism drops fail the Action.

That rule exists because of a bug that ran silent. The recorder arms on a world card's first tick, and only continues an existing recording when the previous state was Dying or ScoreTick. The check compared that previous state after the update call had already performed the transition, so it always saw a card, the continuation branch was dead code, and a death respawn re-armed the recorder: every submitted run containing a death carried only the final life's input segment, replayed to a different score, and got deleted. The player saw SUBMIT FAILED and moved on. The regression tests that caught the next one (TestServeDeathRunRecordingE2E, TestVerifyPendingSystematicDropFails) are tripwires planted at exactly that gap.

The engine version discipline is the price of replay verification. board.EngineVersion is bumped on any gameplay or level change, currently 2026.08.31a (the a marks a same-day coin-reachability correction). Forgetting to bump is worse than bumping. Live submissions get deleted at the next verification pass while looking correct. For postmortems there is mario -dump-replays N to export recent recordings with metadata, mario -replay FILE for a tick-by-tick trace of transitions and death causes, and -trace-window to trace a specific window of a run.

One row claimed 3300 and replayed to 3300 at the commit it was recorded on, but 1500 on current main. The recording, the player and the verifier were all correct; only the engine had moved. A mismatched row is judged at its era. Check out that commit in a worktree and replay the recording there before suspecting the recorder.

The recordings also cut the other way. They autopsy the player's own bug reports. One SSH player reported the big pit jump early in level 1-2 as impossible, and the geometry half-agreed. At walk speed (0.085 tiles per tick) a jump covers about 3.5 tiles and the pit is 4 wide, so a walking jump can never clear it. Running covers about 5.9. The final attempt was textbook (full speed, takeoff one tick from the edge), but the recording showed Run dropping to zero on the tick after the jump press. Air control immediately clamps horizontal speed to walk max, and the player died at 64.215, 0.78 tiles short of the far side. The counterfactual closes the case. Patch that single input lane of the recording (Run held through the airborne window) and the same jump lands safely on the pipe top at 65.8. The real defect was discoverability. Every jump in the entire recording was a walk jump, because nothing on the SSH surface ever said run existed. The report shipped the in-game X TO RUN hint and the -trace-window postmortem tool (17e86a0).

Full speed, perfect takeoff, and death 0.78 tiles short. The recording knew why.

The recording format itself is tiny, run-length encoded, {"v":1,"ticks":N,"runs":[[mask,count],...]}, where the mask is a 16-bit bitmask of the input struct. The bit numbers are a frozen wire format, documented as such in the source, because every stored recording decodes through them and renumbering would rewrite leaderboard history. The cap is 130,000 ticks, about 36 minutes at 60 Hz.

Running the verifier locally needs no dashboard secret either. The repo contains a from-scratch PostgreSQL wire client, internal/pgwire: the v3 simple-query protocol, a TLS upgrade negotiated through SSLRequest, and SCRAM-SHA-256, MD5 and cleartext authentication, with the server signature verified, all on the standard library. It connects as the postgres role, which sits outside row-level security, so the database password alone is enough to read and verify pending rows. The dependency rule has now produced two from-scratch network protocols, an SSH transport and a database client, and the second one exists so a long-lived secret never has to sit on a dev machine.

No tracking, and nothing written to disk

The obvious anti-abuse design is device fingerprinting. It is the wrong tool on both axes. Cooperative users get tracked and fragmented across identities, hostile users stay untraceable, and a hash of identifying signals is pseudonymised personal data, not anonymous data. So there is none.

The native binary writes nothing to the player's machine: no config file, no input-calibration cache, nothing. Player identity is process-lifetime only: a fresh UUID per launch. Clearing your traces means restarting the game, which is the correct consent story. The only storage anywhere is the browser build's localStorage (c81ce7f). The cost of that choice is paid in the rate limits and proof-of-work above, which is a fair trade for never having a file to leak.

The feature we deleted from git history

For about forty minutes, the server knew who you were.

The idea: SSH clients volunteer their entire keyring during authentication. A server that denies every publickey probe (without ever asking anyone to sign) watches the client walk its whole agent and identity-file set, one public key at a time. Match those against github.com/<login>.keys, and a player who connects as their GitHub login gets the leaderboard name entry pre-filled. Editable, of course, but a nice touch. Connect as Daviey@mario.baby and DAVIEY is just there.

The wire details were lovely, in the way that costs afternoons:

  • RFC 4256 numbers keyboard-interactive's info-request at 60, the same number as publickey's PK_OK, and the response at 61. An off-by-one there isn't a negotiation failure; it's a client-side protocol error: rcvd type 61.
  • OpenSSH 8.8 and later refuse to probe RSA keys at a server that never sent an EXT_INFO server-sig-algs after its first NEWKEYS. Without that one extension message, every RSA key on the planet silently declines to introduce itself.
  • Keyless players still had to just work. Keyboard-interactive with zero prompts: a compliant client auto-answers an empty info-request without a single keystroke or a TTY. Batch-mode clients cannot do kbd-int at all, which quietly locked the health-check canary out until it learned BatchMode=no.

It shipped, validated against real OpenSSH builds, deployed to both endpoints. Then I ran the reference implementation.

ssh whoami.filippo.io is Filippo Valsorda's public demonstration of this exact enumeration. It watches your client offer its keyring, matches the keys against a crawled database of public keys from every GitHub account, and greets you by name: no username typed, no signature given. Run it once and the framing inverts. What I had built was not a login convenience; it was a deanonymisation service with an arcade attached. Any player whose SSH key was also their GitHub key could be identified on connect, by a game server, without consent or indication, and the guesses were being written to telemetry columns.

The arithmetic didn't survive that framing. The feature's entire value was an editable pre-fill that only fired if the player already knew to type their GitHub login. Against it: enumerating every visitor's keyring, storing identity guesses, an auth state machine with three more failure modes, and a broken client class. Reverted the same evening, fully: main force-pushed back so the commits are gone from the repository (which is why this section links to nothing), the telemetry columns dropped from the live database, both endpoints rolled back, the canary restored.

The previous section says there is no fingerprinting. The strongest evidence is what happened the one time identity crept in.

It was removed so thoroughly that git has forgotten it ever existed.

One level a day

Daily mode generates a new challenge level from the date seed. The same level for everyone on a given day, with its own leaderboard partition (mode='daily' plus the day, read through board_rows). The generator is deterministic too, which means the daily level is replay-verified by the same machinery.

A generated level is only as good as its hardest jump, so the generator bounds the clearances structurally: pits at most 4 tiles wide because a full-speed running jump covers about 5, pipes at most 3 tall, mid-level stair sets at most 4 steps. The tests check the shape of 30 generated levels: pit widths, plants sitting on pipe mouths, and player start and flag standing on solid ground. When a level was too hard, the fix was not "make Mario jump higher" but to encode the reach bound into the generator and let the tests reject the bad seeds.

The first version of that proof had a hole, and a player fell through it. The daily for 30 August carried coin rows nobody could collect, and the geometry agreed with the player. Both coin emitters could place their shelf five tiles above the floor, a full jump rises 4.4, and the coins sat another 1.2 above the shelf top. The shape tests counted pits and plants but never asked whether a coin can be collected.

The fix is a proof, not a rule of thumb. engine/reach.go flood-fills every tile a small Mario can stand on, starting from the spawn, using the engine's own tick physics as the probe: run and walk, both directions, full jumps from three run-up lengths, cut hops for coins under ceilings, walk-offs for falls. A coin no scripted run ever touches is a bug. The sweep covers the seven built-in levels and every month-day seed the generator can produce, runs in seconds, and on its first pass found the same five-tile shelf in two of the built-ins, whose shelves carried no bound at all. Coin shelves are capped at four tiles now, the same bound as stairs, and the check runs on every push.

One codebase, every surface

The library origin shaped every surface. The engine lives in an importable library (package mario) with thin command-line entry points, because embedding meant the game could never assume it owns the process: no global state, a clock the host drives (App.Step() advances one tick; the host owns the timer), and input delivered as bytes the host decodes. Every later surface, terminal to UEFI, fell out of that discipline for free.

The browser build did not start as pixels. The first version embedded ghostty-web, a WebAssembly terminal emulator, and piped the game's ANSI stream into it. No new render code; the page was literally a terminal. It shipped with an unavoidable flaw. At any browser zoom that is not an exact integer, the browser resamples the emulator's canvas, and the player saw "alternatiting black lines across the screen": dark bands every other cell row, about 15 px apart at 110% zoom. The emulator's backing store was pixel-exact (a 1075×680 backing behind an 860×544 element at device pixel ratio exactly 1.25, frames byte-identical) and image-rendering: pixelated changed nothing. The resampling happens above the canvas, where a terminal emulator cannot reach.

So the page stopped being a terminal that same evening; the game moved off ANSI and onto raw pixels over a plain canvas.

The same engine compiles to every target. The native binary is the obvious one. The browser build is Go to WebAssembly: the page provides marioFrame for the pixel canvas, marioBoard for the leaderboard DOM, marioSfx for a WebAudio synth, and the game exports marioFeed. It ships as a PWA with a service worker, an on-screen touch gamepad (virtual joystick with tilt-to-run, A/B buttons, a draggable arrange mode that persists in localStorage), and a boot screen that is a level of the game: Mario reaches the flagpole at 100% download.

The loader is honest by construction: a host that strips Content-Length gets a progress bar that drops the total rather than inventing a denominator, the fade-out fires on the first painted game frame rather than the download finishing, and a corrupted body surfaces as the browser's own compile error naming the wasm magic bytes instead of a dead black screen.

The on-screen pad feeds the game kitty-protocol press/release pairs rather than plain bytes, because a bare byte is a legacy press whose hold decays in the mapper after about a fifth of a second: pad-held movement would stall after one step. That regression killed phone movement for an afternoon; the capture paths that need plain bytes decode the pairs back.

Back on the terminal surface, sound is one byte: BEL. It's the only audio channel every terminal guarantees (a C0 control every parser executes even mid-sequence), so coin, stomp and fireball events all collapse onto it, throttled to one BEL per 120 ms so a stomp chain doesn't machine-gun. The attract demo stays silent, because a title screen must not beep at people walking past (ecc713d). What the player actually hears is their terminal's bell setting; gnome-terminal ships with it off. The browser build gets the same engine events as a real WebAudio synth instead.

The Android APK is a thin WebView shell around the same web bundle, locked to landscape. Chromium blocks fetch() on file:// origins, so the activity intercepts requests to a virtual scheme and serves the bundled assets, and it replaces the service worker with a no-op one, because a cache-first worker would otherwise serve the previous release's wasm after every app update.

The iOS .ipa is built on Linux with no Mac and no Xcode: clang targeting arm64-apple-ios, lld, and ldid for an ad-hoc signature, wrapping a WKWebView shell in a from-scratch Info.plist. Users sideload it with AltStore or Sideloadly. The macOS .app is a universal (fat) Mach-O assembled by a pure-Go tool, no Xcode either. There is also an AppImage, a Nix flake, a .deb and a .rpm for each of the five Linux architectures, and an AUR package for local builds. make release cross-compiles 17 OS/arch pairs from one tree.

The bootable targets are the odd ones out. make efi produces a single-file UEFI boot image: a tiny custom Linux kernel (EFISTUB, simpledrm, evdev) with an initramfs containing only the static game binary as /init, driving the same App.Step() at 60 Hz and blitting RenderPixels to /dev/fb0. make iso wraps the same payload in a BIOS-bootable hybrid ISO via xorriso, and make iso-qemu smoke-boots it headlessly in QEMU.

The packaging tools follow the dependency rule. tools/mkdeb builds a .deb by hand (ar, tar, gzip), tools/mkrpm writes an RPM v3 (lead, digest-only signature header, header, cpio payload), tools/mkapp assembles the macOS bundle, tools/mkipa the iOS one. All of them are deterministic: the tests parse the archives back and check the bytes. Determinism here matters because re-running a release run must produce identical artifacts.

Tests, CI, and the bugs only a machine catches

The test suite is 17,270 lines against 17,160 lines of product code, stdlib testing only, no assertion libraries, no golden files. Assertions are programmatic: pixel reads through Frame.At, string-contains on ANSI output, geometry checks. The categories worth calling out:

  • Determinism: full rendered runs byte-compared.
  • Viewport sweeps, plus cloud tests that assert the pixel-level title-band suppression is non-vacuous.
  • Wire round-trip: a simulated terminal model parses the emitted byte stream and reconstructs the screen.
  • Fake backends: fakePostgREST and injectable submit/fetch functions keep leaderboard tests offline; LIVE=1 gates the real-Supabase E2E.
  • Real-client E2E: SSHE2E=1 drives an actual OpenSSH client through the from-scratch server, including a latency guard.

One more from the bugs-only-a-machine-catches file, except here the machine was complicit. A leaderboard hint's fit check read hintY+5 <= f.H-5, and hintY works out to f.H-5, so the check reduces to f.H <= f.H-5: false at every viewport size there is. Comments still described the hint, and the test asserted the hint's screen band through the same broken gate, so the suite stayed green while the feature rendered nowhere for days. The fix's real content was the test: assert the hint draws at some viewport, and at all of them (8313e0a). A test written from the same misunderstanding as the code is a witness for the defence, not a tripwire.

CI runs on a self-hosted runner. Push to main: make check (fmtcheck, vet, test), native build, the full 17-target release matrix, and a WASM compile-check. Tag push: the same gate, then the per-target build matrix, packaging, a GitHub release with SHA256SUMS, and a Pages deploy that fires via workflow_run because the Pages environment's protection rules reject tag refs. Release notes are generated from the commit log by an agent and land in the release body and in CHANGELOG.md.

The runner image has no C toolchain, which means the race detector can never run in CI (make race is a local-only gate) and every Makefile goal must force CGO_ENABLED=0 or it dies compiling runtime/cgo. The web deploy to mario.baby is a tar-over-ssh to a NixOS box, extracted to a release directory and cut over with a single same-filesystem mv -T onto a symlinked content path, so a failed deploy leaves the old site standing. TLS is Let's Encrypt via ACME DNS-01 (the A/AAAA records are DNS-only, grey, because a proxied record would eat the SSH that reaches the game on port 22).

The worst web failure never touched game code. The wasm binary has no environment to read, so its Supabase credentials only exist through a -ldflags -X injection wired in the Makefile. A security rework kept the $(WEBLDFLAGS) reference and deleted the variable's definition, and make expands undefined variables to an empty string, so for three days every web build shipped a board that read OFFLINE: GitHub Pages, the APK and the first mario.baby deploys (b498abb is the restoration). The credential guard in make web validates the variables but cannot see the flags line that fails to carry them. Since v0.8.0 the tripwire is the build itself: make web greps the wasm for supabase.co and fails when it is missing (9bb196d). The same symptom had a second cause: the service worker was cache-first, so returning visitors kept the previous release's wasm even after the fix deployed. It is network-first now, because a release has to go live on the next page load.

Root with no capabilities is less than a user.

The AppImage job died in bubblewrap with EPERM. Jobs in that container run as uid 0, and bwrap, finding itself root, skips its unprivileged user-namespace path and calls unshare(CLONE_NEWNS) directly, which needs CAP_SYS_ADMIN. The runner unit's capability bounding set was empty, so root was denied a syscall an ordinary user would have passed through the namespace path. The root cause came from running strace inside the CI job, and the fix was one line of systemd configuration.

What six days of releases bought

The release cadence (v0.1.0 to v0.7.1 in six days) was a side effect of the architecture, not a goal. The leaderboard is live and public from day one, so every gameplay change has to bump the engine version, and every SSH or input change has to survive a real terminal on a real link. The bugs that shaped the codebase are the ones players hit:

  • A kitty keyboard level pushed on the wrong screen left CSI-u garbage in the player's shell after ssh mario.baby exited.
  • The recorder-wipe bug above, found by scripting a pty playthrough whose 400-point run replayed to 0.
  • A checkpoint respawn that killed the player at tick 0, because a level reload puts every enemy back at its spawn point and the auto-picked checkpoint column sat exactly on one.
  • A 2-pixel gap between the castle roof and the flagpole mast in 2-4, found by looking at the level the way a player does, fixed in the most recent release.
  • A coin row no jump could reach, reported the day after v0.7.1. Three levels had all placed coin shelves five tiles above the floor, 0.6 past the apex of a full jump; the reachability proof above exists because of it.

Each one is small. Each one is invisible to a human who tested "it works".

The seventh day

The seventh day shipped v0.8.0, and it shipped no levels, no enemies and no features. It shipped a broom.

A debt audit had walked the tree with six read-only scouts, and the fix wave landed as 42 commits between the v0.7.1 and v0.8.0 tags: the 1,596-line render.go split into seam files (camera, palette, screen, world, title, hud), the SSH server's 1,179-line server.go split the same way, the input hold model extracted to a file of its own, and the dead code the audit turned up simply deleted (ed3666a, 3a249d7).

Thirty-seven of those 42 commits carry github-actions[bot] as the author, because the fix wave ran as parallel agents on a shared tree. The reason that is a calm sentence instead of a terrifying one is the same determinism the rest of this post keeps leaning on: v0.8.0 pins the engine's level bytes in tests, so a 42-commit restructuring that changes nothing shows up as nothing (5f34243). A robot can hold the broom when the floor is tiled with tripwires.

The scraps that rode along, because no broom pass is pure: a physical backspace now deletes a character in name entry (it did not before), r restarts from the game-over ask, and the site serves a SECURITY.md (9a6f5dc, b685015).
